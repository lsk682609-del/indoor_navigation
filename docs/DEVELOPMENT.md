# 开发约定与测试顺序

实车入口已新增，参考 [实车运行说明](../real_robot/README.md)。下文默认描述原仿真入口；
实车使用独立的配置、构建结果及 ROS 域，并接入原室内地图定位工作空间。

## 当前坐标与模型

室内地图为局部米制平面坐标，`lla_mode: 0`，不需要地理原点、RTK 或 GPS 目标。
默认车体模型、传感器安装和轮式动力学来自原仿真，保留雷达/IMU/相机。
导航只消费雷达点云和仿真里程计；不使用相机控制。

完整路网显示由 `road_network_display.py` 独立发布：`/car1/road_network` 为节点、编号和边，
`/car1/indoor_environment` 为世界碰撞几何背景。两者都是持久的 MarkerArray，
无需下发目标即可显示。当前背景支持平面 SDF 盒体、直立圆柱及嵌套的平移/偏航姿态，
遇到其他几何会报错并保留路网显示，避免生成不准确的背景。
`run_display.sh` 可把显示附加到旧的运行实例；新版整体启动已包含显示节点。

```text
map                         input_bridge 根据仿真 /odom 发布
└── base_link               地面导航参考点
    └── base_footprint      本工程发布恒等静态变换
        └── chassis        robot_state_publisher
            └── livox_frame
```

雷达相对地面参考点平移 `(0.24,0,0.30)` m；车轮碰撞包络约 0.46×0.46 m，
导航 footprint 包含雷达前伸，取 x=[-0.23,0.275]、y=[-0.23,0.23]，另加 0.02 m padding。
仿真 /odom 的坐标来自 Gazebo 世界；bridge 直接转成 map 命名，不提供真实 SLAM 或地图匹配。
控制器消费原始 /odom 的车体速度；bridge 的差分线速度现已转为车体坐标，实车优先读取底盘速度反馈。

## 新场景

1. 修改/新建 world，保持小车出生点在可通行地面上。
2. 按实际走廊中心和转角编辑路网，边必须完全位于可通行区域。
3. 路网文件是自定义分段文本，并非标准 YAML 映射；节点为
   `id type map_id x y z lat lon alt`，边为 `id type map_id from to obt`。
   无经纬高时写 `nan nan nan`。边类型 0 为双向。
4. `max_snap_distance` 必须覆盖相邻节点中间位置，但不能大到吸附隔墙道路。
   当前值 2.1 m 对应最长 4 m 边。节点吸附无法独立判断隔墙情况，需结合地图和目标约束。
5. 保持 `edge_snap_enabled: false`，原 SNN 对边吸附临时节点的支持尚需单独修复和测试。
6. 更改后运行静态检查及导航测试。`check_assets.py` 只适配当前轴对齐矩形场景；
   新增旋转墙、动态模型或其他几何时，必须扩展检查器。

启动其他场景可传 `world:=... topo_map_path:=... params_file:=...`，三个文件须匹配。
当前启用自动窄门伺服，通过实时点云确认通道位于当前路线上，不配置原场景 `(10.5,8)` 的固定门心。

室内箱体绕障采用 0.5 m 膨胀半径、2.0 的膨胀衰减系数和 `lethal_cost: 253`。
先前的硬阈值 140 会拒绝现场窄通道中的 200–245 软代价，当前以软代价引导远离障碍，
Theta* 邻居、视线和原路折线检查均使用此规划阈值。局部目标按路网弧长限制在前方 4 m，
避免在滚动窗口边缘规划到拐角后的远端目标。普通室内绕障不启用窄门专用的近点汇入逻辑，
无解时停车重试，不沿已经判为受阻的原路继续前进。
已生成的绕障路径使用 253 执行阈值，并额外逐段检查带 padding 的车身轮廓，
避免软代价抖动引起反复重规划；新障碍、未知区域或越界仍使路径失效。
启用现有 CostmapPathSmoother，最大点位偏移限制 0.15 m、连续检查步长 0.025 m，
按候选航向检查完整轮廓；平滑失败时回退原始 Theta* 路径。
最高线速度 1.0 m/s，控制频率 20 Hz；速度相关预瞄范围 0.4–1.0 m，时间 0.8 s。
加减速度分别为 0.5 / 1.0 m/s²，前向减速净空扩大至 1.2 m，停车净空仍为 0.35 m。
曲率限速、前向停车保护和运动碰撞预测均保留。

窄通道处理沿用原 `gazebo_net_nav.yaml` 的 ALIGN/CROSS/EXIT 激光测距伺服。
两侧边缘须处于当前路线附近，感知宽度在 0.62–1.20 m 范围内；默认穿门速度
0.25 m/s，先居中对准再穿越，门框近场丢失后利用里程计纠正锁定航向。
门区全程保留新鲜点云检查、前向停车和车身碰撞预测，真实 254 障碍不会被忽略。
进入 ALIGN 前还预检查整段车身能否到达门内，避免斜向观测把过窄门洞误判为宽缝。
自动门模式不启用原固定门场景的历史汇入点、无解沿原路前进等专用分支。

本副本同时修正 Livox 仿真距离换算：ODE 射线由 `minDist=0.10 m` 处开始，
`contact.depth` 是距射线起点的长度，发布点云时补回 minDist。此前漏加导致
障碍向雷达方向偏移约 0.10 m，进一步压缩了本可通行的门洞。原工作空间未同步修改。
`tests/lidar_gate_geometry.py` 在静止状态把实际点云与独立已知的门框碰撞表面比较，
要求中位误差 <0.01 m、95% 分位误差 <0.03 m。

绕障停顿修复：前向净空先限制目标速度，再执行加减速限幅，避免上一周期输出
反复乘净空系数而陷入几毫米每秒的爬行。普通对准进入角为配置的 0.5 rad，
接近停车区（净空 ≤0.55 m）时允许以 0.25 rad 提前对准，退出角为 0.10 rad；
原地对准期间保持状态，避免在 0.12 rad 附近逐周期切换停车与前进。
没有可用全局尾段的临时绕障路径，在距离末端 0.60 m 且最终目标仍超过 1.0 m 时
退出冻结并立即重新评估路径，避免在临时末端减速后等待 10 s 进度检查超时。

## 逐步测试

| 阶段 | 内容 | 验收证据 |
| --- | --- | --- |
| 静态资源 | 节点连通、路网/墙体净距、源码独立 | check.sh 输出 |
| 全局规划 | 所有节点对，包含同起终点 | planner_matrix.py 全通过 |
| 基础导航 | 直线、转角、多段、返回 | JSON 状态及真值位置误差 |
| 局部避障 | 单箱、偏置障碍、窄道 | 路径、轨迹、独立碰撞/净距检查 |
| 任务控制 | 取消、替换目标、暂停 | 状态与实际速度一致 |
| 异常 | 点云中断、定位中断、通道堵塞 | 按设计停驶或失败，需新增故障注入测试 |

只把已经执行并有证据的项目标为通过。现有层 2 重规划会重新请求路径，
但尚未把局部障碍自动转成禁用路网边，不能保证堵路后会自动选择环路另一侧。
同一配置重复测试时，记录模型出生位姿、目标序列、版本、耗时、真值误差和失败原因。

局部规划失败与边界回归可执行 `./scripts/test_planner_failure.sh`，
使用 ASan/UBSan 检查不可达、地图外坐标、边界 LOS、反复重规划及窗口变化。
这项检查不需要启动 Gazebo。

`./scripts/test_detour_footprint.sh` 检查软代价变化时复用路径、新障碍使路径失效、
中心点可通行但车身前角碰撞、候选航向变化、轮廓越界及未知区域。
同时检查恒定净空下速度不会累乘衰减、曲率和加速度限幅、原地对准状态防抖、
小角度抖动不停车，以及临时绕障段续接与最终目标减速的区别。

`test.sh --obstacle` 需要小车位于原点 0.5 m 范围内，会在 `(3,0)` 放置
0.5×0.5×0.6 m 静态箱体并下发 `(6,0)`，要求收到非空 Theta* 路径后到达。
测试结束会删除箱体。该检查验证绕障链路被调用及到达，不能替代全轨迹碰撞检测。

`./scripts/run_avoidance.sh` 启动截图复现世界，保留 `(0.251,1.637)` 附近的 1 m 箱体，
小车从 `(9,0)` 朝西出发。可下发 `(0,4)` 再下发 `(0,0)` 测试正反向绕障。
`./scripts/validate.sh --avoidance-isolated` 会在 ROS 域 189 / Gazebo 端口 11356
独立执行这两项和小箱体测试，不覆盖当前 GUI 的目标。
每项保存 Gazebo 真值轨迹，并使用包含 padding 的实际车体矩形与箱体矩形计算采样净距。
成功条件包含到达、生成绕障路径和最小采样净距大于 0.02 m；这不是连续时间接触监测。

## 实车接入边界

`navigation.launch.py` 可单独启动导航，参数包括 `use_sim_time`、`odom_topic`、
`cloud_topic`、`cmd_vel_topic`、`params_file`、`topo_map_path`、`publish_base_tf`。
它不会启动底盘驱动或定位节点。

实车输入里程计的位姿必须已经表达在路网 map 坐标中，并对应当前 base_link 参考点；
速度应表达在车体系。雷达点云与模型外参必须匹配。
若定位仅提供重启原点不同的局部里程计，必须先加入地图定位/坐标对齐，
不能通过改 header.frame_id 代替真实变换。

当前 bridge 会发布 map->base_link，因此外部定位不能同时发布冲突的同一 TF 链。
如果采用标准 map->odom->base_link，应先重构 bridge 的 TF 发布逻辑，再接入。
默认脚本 ROS_LOCALHOST_ONLY=1；电脑与实车分机部署时需要单独配置网络、ROS 域和 TF。
本工程尚未提供实车完整定位及其失效保护验证。
